# Dynamic vs preallocated K/V: a CPU tradeoff, not a speedup

2026-11-22 MYT. Optional preallocation replaces K/V growth copies with a
fixed reserve, but that does not guarantee faster requests. We compared the
two existing implementations with identical input, weights and output. On
this CPU and these two fixed workload shapes, **every median paired
preallocated/dynamic elapsed-time ratio exceeded 1.0**. No runtime or default
cache policy was changed.

## Run it

```bash
python -m pip install .
# Linux CPU timing: first eligible logical CPU, pin before importing Torch
transformer-cache-tradeoff --output cache-tradeoff-local.json
# Always real fixture parity plus retained-storage checks, no timing or affinity
transformer-cache-tradeoff --check-only --output cache-tradeoff-parity.json
# Audit saved calculations and source identities; no inference, no Torch import
transformer-cache-tradeoff --audit results/cache-tradeoff-v1/report.json \
  --output cache-tradeoff-audit.json
```

The module equivalent is `python -m transformer_diagnostics.cache_tradeoff`.
Output paths must be new. Run the timing command on Linux with a readable
`/proc/self/task` and permission to pin its own threads. On other platforms use
check-only or audit. No model, corpus or historical checkpoint download.
GitHub CI runs actual check-only, no timing thresholds.

## What was timed

Same procedural float32 fixture, 99,968 parameters. Canonical artifact and
tensor SHA-256 are in the [raw report](../results/cache-tradeoff-v1/report.json).
No training or trained-model quality claim. Pre/post checks used the real shared
request and full-prefix forward: all 96 generated byte IDs exactly matched,
cache arms had zero observed difference at compared logits, and their maximum
absolute difference vs full-prefix was `1.0728836059570312e-6` under combined
atol=rtol=1e-5. Model and checked snapshots kept the same tensor identity.

One constructor-only comparison, plus two request modes for each shape:

- Constructor-only: new decoder, including validation, deep-copied snapshot
  and, for the preallocated arm, reserved storage.
- New session: constructor plus first complete shared cached request.
- Reused session: existing snapshot, complete shared cached request including
  reset of prior sequence. Identical forward counts (1 prefill, G−1 appends).
  The final generated byte is returned but not forwarded.

Each cell has six warm-up pairs followed by **30 alternating AB/BA pairs**.
One call per arm in each pair, with result/decoder alive through stop.
No profiling, output comparison, or storage inspection in the timing boundary.
Setup and teardown separate as described in the [protocol](cache-tradeoff-protocol.md);
nothing is inferred by subtracting medians. The clock is monotonic wall time
with an observed 60 ns median empty boundary, not subtracted.

## Observations from the first eligible run

Linux 6.18.57 x86-64, AMD EPYC 9V74, Python 3.12.14, PyTorch 2.14.1+cpu,
deterministic inference, intra/inter-op and BLAS settings at 1. The runner
selected CPU 0 from eligible 0–8 before importing Torch. Its one observed
native thread had that exact mask at both checks. This pins our process, not
the host: unknown neighbors, end-to-end cloud noise and a fixed case order
remain limitations.

Times are ms. Ratio means **median of individually paired preallocated/dynamic
times**, not the ratio of medians. A value above 1 means preallocated took
longer in the median pair. Display rounded; raw order, min/max, p90, and
first-arm stratification are included in the report.

| Phase | Shape | Dynamic median / p90 | Preallocated median / p90 | Median paired ratio | Preallocated quicker pairs |
| --- | --- | ---: | ---: | ---: | ---: |
| Constructor only | shared | 2.100 / 2.354 | 2.122 / 2.423 | 1.015 | 12/30 |
| New session | B2/P16/G16 | 13.148 / 16.765 | 13.577 / 16.994 | 1.051 | 10/30 |
| Reused session | B2/P16/G16 | 10.754 / 13.424 | 11.748 / 13.118 | 1.065 | 9/30 |
| New session | B2/P32/G32 | 26.424 / 31.202 | 27.240 / 37.905 | 1.064 | 10/30 |
| Reused session | B2/P32/G32 | 22.050 / 26.088 | 23.134 / 25.614 | 1.048 | 8/30 |

The four request comparisons did not show a median latency gain here, although
the two reused-request p90s are lower for preallocation in this finite sample.
These are descriptive values from one run/one machine, not tail-latency service
evidence or a significance test. The whole decoder was timed, not only the
concat/copy operator, so these results do not isolate a causal mechanism or
generalize to longer context, different hardware, GPU, or batch sizes.

## Active K/V versus retained backing, outside timings

Both arms had the same active payload: 63,488 B at length 31 and 129,024 B at
length 63. Distinct untyped storage bytes, independently enumerated:

| Arm | At construction | After short / long request | After reset |
| --- | ---: | ---: | ---: |
| Dynamic | 0 B | 63,488 / 129,024 B | 0 B |
| Preallocated | 131,072 B | 131,072 / 131,072 B | 131,072 B |

The static arm retained four distinct 32,768 B storages with stable pointers.
The dynamic reset result means no K/V tensor storage owned by the session, not
that memory was returned to the OS. The preallocated reset is not erasure.
Backing and aliased active views are not additive. These observations are not
RSS, peak memory, memory bandwidth, allocator behavior, or throughput.
